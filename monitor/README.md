# 自动检测维护说明

## 执行方式

- GitHub Actions 每 4 小时执行一次：北京时间 00:17、04:17、08:17、12:17、16:17、20:17；调度使用 UTC，可能延迟。
- 将 workflow 合并到 GitHub 默认分支后，打开 **Actions → Check IP APIs → Run workflow** 可立即检测。
- 工作流从默认分支读取脚本和配置，但只向独立的 `monitor-results` 分支写入结果，绝不提交回默认分支。需要启用 Actions 并允许 `GITHUB_TOKEN` 的 `contents: write` 权限；无需额外配置个人访问令牌。
- 默认分支保护可以保留。组织策略若禁止机器人创建或更新 `monitor-results`，需要为结果分支配置合适的权限；不要关闭代码分支保护。
- 公共仓库长期没有活动时，GitHub 可能停用定时工作流（通常为 60 天），可在 Actions 页面重新启用。

## 测量口径

每个配置项预热 1 次，再串行请求 5 次，每次测量前间隔 1 秒。单次网络操作超时为 10 秒，整个工作流最多运行 15 分钟。

平均响应计时从发起请求到响应体读取完成，包含连接、TLS 与网络传输时间，不包含 JSON 校验；仅统计通过 HTTP 2xx 和业务字段校验的样本。每次请求独立建立连接，不是浏览器复用连接后的延迟。预热不计入成功次数或平均值。

| 成功次数 | 可用状态 | 平均响应 |
| :--- | :--- | :--- |
| 5/5 | ✅ 可用 | 5 次成功请求的平均值 |
| 1/5 至 4/5 | ⚠️ 不稳定 | 仅成功请求的平均值 |
| 0/5 | ❌ 不可用 | — |

此结果代表 GitHub 托管 Runner 的网络视角，不代表国内用户体验，也不是全天可用率。接口失败会记录为检测结果，不阻止其他接口检测；脚本、测试或推送失败则会使工作流失败。

结果分支的 `latest.json` 保存最后一轮时间、环境、源代码版本、成功次数、平均响应和失败原因，`README.md` 展示结果表格。报告中的文档链接指向本轮使用的源代码版本，不会错误链接到没有接口文档的结果分支。每轮结果还会作为 Actions artifact 保留 30 天。

## 避免自动更新冲突

- 代码分支只维护接口配置、文档、脚本和静态首页，不再跟踪 `monitor/latest.json`。
- 检测脚本仅写入被 Git 忽略的 `monitor/output/`，不会修改代码分支 README 或暂存区。
- 发布脚本使用独立临时索引，只把生成的 `README.md` 与 `latest.json` 提交到 `monitor-results`；首次运行自动创建该分支，后续保留结果历史。
- 发布目标固定为 `refs/heads/monitor-results`，不依赖当前分支，不使用强制推送。并发修改代码分支不会影响结果发布；极少数并发修改结果分支的情况会安全拒绝推送，重新运行即可。
- 不要将 `monitor-results` 合并回代码分支，也不要手动维护里面的文件。正常人工协作仍需同步代码分支，但不再因为定时检测而出现代码分支分叉。

迁移工作流推送后，在 Actions 手动运行一次即可生成结果页。在此之前新结果链接可能尚不存在。旧工作流若仍在运行，应先取消它，再运行新版本，避免旧任务最后一次写回代码分支。

## 新增接口

编辑 `monitor/apis.json`，在 `apis` 数组增加一项：

- `id`：唯一且稳定的接口标识。
- `name`、`url`、`method`：名称、HTTPS 地址和请求方法。
- `category`：`both`（两者均支持）、`local`（仅本机）或 `target`（仅指定 IP）。
- `body`：可选 JSON 请求体；GET 请求通常省略。
- `headers`：可选请求头；不要提交令牌等敏感信息。当前设计面向公开 JSON 接口。
- `expect`：固定值业务判定，例如 `{"found": true, "target": "110.96.1.1"}`。所有字段必须匹配，支持 `location.country` 形式的嵌套路径，以及 `data.0.origip` 形式的数组索引（从 0 开始），类型也必须一致。
- `validate`：动态字段判定，例如 `{"data.ip": "ip"}`；`ip` 要求合法 IP 字符串，`nonempty_string` 要求非空白字符串，`string_list` 要求非空字符串数组且至少一项非空白。`expect` 与 `validate` 至少提供一条规则；同时配置时全部规则均需通过。
- `info`：接口返回信息摘要，保留在配置中，首页表格不展示。
- `doc`：相对于仓库根目录的接口文档路径。

一个配置项代表一种具体请求，不会自动遍历接口的所有能力。例如宝塔当前探测指定 IP 模式，不单独验证本机 IP 模式。

本机 IP 接口使用动态字段判定，不固定某个出口 IP。腾讯新闻、乐视与 IPIP 均按本机查询收录；检测运行于 GitHub Actions 时，接口返回的是 Runner 的出口 IP，而非你的电脑 IP。报告不保存响应体，本机接口示例统一使用 `110.96.1.1` 构造展示，并注明不是该接口的实测响应，不公开本机出口 IP。

新增接口后，运行 `python scripts/check_apis.py --catalog-only` 更新首页静态目录，再与配置一并提交。该命令只替换 README 中 `ip-monitor:start` 与 `ip-monitor:end` 之间的目录，不发起请求，不写检测结果；定时工作流不会执行此命令。

## 本地运行

需要 Python 3.10 或更高版本，无第三方依赖。在仓库根目录运行：

```bash
python -m unittest discover -s tests -v
python scripts/check_apis.py
```

第二条命令会请求配置中的第三方 API，并生成 `monitor/output/README.md` 和 `monitor/output/latest.json`；环境会标注为本地运行。代码分支不产生文件变更，也不会自动发布本地测速结果。

仅在输出目录生成待检测展示、不发送请求（覆盖本地输出目录的报告，不影响源文件或远端结果）：

```bash
python scripts/check_apis.py --initialize
```

`--output-dir` 可指定独立报告目录。`--source-ref` 指定报告文档链接的代码版本，工作流自动传入实际检出提交。

`python scripts/publish_results.py` 会将输出目录发布到远端结果分支，属于写操作，一般仅由 Actions 调用。它不会推送当前代码分支，也不会把其他本地文件加入结果提交。
